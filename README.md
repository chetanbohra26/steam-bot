# Steam Market Buy Order Bot

A Node.js bot that places lowballed buy orders across liquid Counter-Strike 2 weapon skins, aiming for opportunistic fills to flip — not a "fair price" bot.

## Setup

1. Install dependencies: `npm install`
2. Copy `.env.example` to `.env` and fill in your Steam username and a **base64-encoded** password (see the comment in `.env.example` for how to generate it — this is obfuscation, not real encryption, but avoids the literal password sitting as plaintext).
3. Run `npm run pick-items` to build the initial item pool (see below — this takes a while).

## Scripts

- `npm run pick-items` — **currently broken**: its stage 1 uses `search/render`, which returns 404 since Steam's market UI change (seen 2026-11-25). When working, it is a full refresh: scans the market for liquid weapon skins and ranks them by real trade volume ("better horses to bet on"), rebuilding `items.json`. **Slow**: stage 1 pages through the market's most-listed in-band weapon skins (Steam returns only 10 results per page, so ~260 requests at 2s each, ~9 minutes) to collect up to 1,000 candidates, then stage 2 checks volumes with `priceoverview` at ~10s pacing; it prints an upfront estimate, then one log line per item with price, change vs. the pool's cached price, median price, volume and a live ETA. It's the heaviest script, but it only fetches what's needed:
  - Stage-1 candidates are cached for 4 days (so a weekly refresh split over several runs, e.g. across a weekend, keeps one candidate list and skips the rescan) and rescanned after that, so new releases and moved prices show up. A reused list's prices are as old as the list; run `pick-items-priceonly` before `up-noprice` if that matters.
  - Each volume is cached with the time it was fetched and re-fetched after 30 days. New candidates are fetched first, then stale ones oldest-first.
  - A hard cap of 150 `priceoverview` calls per run (the first three bans hit at ~585, but two runs on 2026-11-17 both hit a 429 at call 167). If more are queued, the run finishes normally, writes `items.json` with the saved volumes, and tells you how many are deferred; re-run in a few hours or the next day to finish.
  - The pool is built from the current candidates only, with each item's price taken from whichever is newer: the stage-1 scan or its latest `priceoverview` fetch.
  - If Steam rate-limits it anyway, it stops on the first error, saves progress to `pickItemsCache.json`, and exits with code 1 — re-run after the ban clears (hours) to resume.
- `npm run pick-items-priceonly` (`--price-only`) — refreshes the existing pool's cached price and 24h sales volume in `items.json` from Steam's market listing pages (`listingScan.js`). One page covers every variant of a skin, so the pool needs one request (plus a redirect) per skin: ~440 pages ~8s apart, about 70 minutes. No search or `priceoverview` calls. The pool's items and their order don't change. It stops at the first HTTP error status, rate limit, non-INR page, or 3 unreadable pages in a row (connection errors are retried twice); it keeps what it had already refreshed, skips the order risk check and exits with code 1. It also exits 1 if more than 5% of the pool had no price. It writes `buyOrderAdjustments.json`, flagging any **active** buy order whose reference price moved 20%+ since the order was placed (measured against the price recorded in `orderBids.json` at placement, not the pool's price, so repeated runs don't lose the baseline), with its bid as a share of the new price and a suggested new bid — purely informational, covering moves in both directions. Separately (see `cancelRiskyBuyOrders.js` below), after a scan that wasn't stopped early it automatically cancels any active order whose price has fallen 20%+ below its reference — that one does act, and only on drops.
- `npm run up` — logs in and places buy orders for the top `LIMIT` items in the pool that don't already have one, fetching a live price per item and bidding `DISCOUNT_FACTOR` (currently 60%) of it. Refreshes price/volume in `items.json` and logs every fetch to `priceHistory.jsonl` as it goes. Records each order's reference price and bid in `orderBids.json` as it places it.
- `npm run up-noprice` (`--cached`) — same placement logic as `up`, but uses `items.json`'s already-cached prices instead of live fetches. No `priceoverview` calls at all — ideal right after a `pick-items`/`pick-items-priceonly` run whose data is already fresh.
- `npm run down` — cancels all active buy orders (batched, paced conservatively) and, once verified empty, resets the placed-orders tracking (`placedOrders.json` and `orderBids.json`).
- `node cancelRiskyBuyOrders.js` (`--execute` to actually cancel; without it, dry-run only) — reads the live buy-order list straight from Steam (not local tracking) and cancels any order whose price has fallen 20%+ below its reference: bid at ~60% of market, sitting on a 7-day resale hold plus Steam's cut, so a big enough drop risks turning into a loss. Same batching/pacing as `down`. This is also run automatically (with `--execute` behavior) at the end of every `pick-items-priceonly` run.
- `npm run dry-run` — shows what `up` would place and the total capital commitment, using cached prices only (no live API calls, instant).

## Operational cadence

- **Nightly**: `npm run pick-items-priceonly` — catches fast price moves (e.g. a new-release skin crashing 30-50%+ in days) between full refreshes, and flags active orders worth reconsidering via `buyOrderAdjustments.json`. It runs for over an hour, so don't start another script until it finishes.
- **Weekly**: `npm run down` then `npm run up` (or `up-noprice` if prices are already fresh that day) — refreshes active orders against current prices. Cancel-then-replace resets Steam's price/time queue priority, so this shouldn't be run more often than needed.
- **Weekly**: `npm run pick-items` — full rediscovery/re-ranking, to catch new product releases entering the liquid pool. **Must be on a different day than the `down`/`up` cadence above** (see rule below) — e.g. full `pick-items` early in the week, `down`/`up` later in the week.
- **Never run full `pick-items` and a live `up`/`down` on the same day.** Each script paces its own requests safely on its own, but Steam's IP rate limit appears to be shared across all `steamcommunity.com` market endpoints (`priceoverview`, `createbuyorder`, `mylistings`, `search/render`) rather than siloed per-endpoint — hit this on 2026-09-27 when a `pick-items` run got banned mid-run despite pacing under ~13/min itself, because two `up` runs earlier that day had already used IP budget. `pick-items-priceonly` now makes ~880 listing-page requests (counting redirects); the rate limit for those pages is unknown (only up to ~100 requests tested as of 2026-11-25), so watch the first full runs, avoid same-day `down`/`up` until a few have passed, and never run it concurrently with another script.
- **Keep `priceoverview` under ~500 calls per hour.** A second ban (2026-10-03) hit at ~585 calls in ~62 minutes, even with nothing else running that day, while 535 calls in ~56 minutes (2026-09-28) was fine — so the limit looks like a per-hour count, not a per-minute rate. A third ban (2026-10-11) hit at ~585 calls again at a slower pace, so it looks like a call-count cap rather than a rate; pick-items now paces at ~10s and stops at 150 calls per run after two runs on 2026-11-17 (on different machines, ~6h apart, one with no stage 1 requests) were both rate-limited at call 167, which suggests a smaller budget of ~166 calls that recovers within hours. This is inferred from a few runs, not documented by Valve.
- A fourth incident (2026-11-18) hit the wall far earlier: `pick-items-priceonly`'s per-item fallback fetch (for pool items missing from the stage-1 scan — added that day, see below) got a 429 after only 21 `priceoverview` calls at ~10s pacing. The difference from the incidents above: the same IP had, in the couple of hours before that, run `pick-items-priceonly`'s ~265-request stage-1 scan twice back to back (once that morning, once again during same-day testing) plus several `mylistings` fetches — none of which call `priceoverview` at all. This is the clearest same-day evidence yet for the shared-IP-budget theory in the rule above: the ~166-call `priceoverview` budget looks like it can also be partly consumed by heavy same-session use of other `market/*` endpoints, not just by `priceoverview` itself. Practical takeaway: don't re-run `pick-items-priceonly` (or any full stage-1 scan) more than once in a short window on a day you still need `priceoverview` headroom. The fallback fetch itself degrades safely — it stops on the first 429 instead of continuing to burn the ban, leaving the rest to be picked up on a later run.

## How it works

1. `selectPilotItems.js` finds liquid weapon skins (excluding knives/gloves/cases/stickers and Souvenir items) priced between ₹25 and ₹500, then ranks them by real recent sales volume (not just listing count, which favors oversupplied-but-unwanted items) — the goal is maximizing fill probability, not payoff size per fill.
2. `index.js` takes the top unplaced items from that ranked pool and places a buy order for each at a fixed discount off the current lowest price, with a hard safety guard that refuses any order that isn't strictly below the live lowest price.
3. `cancelAllBuyOrders.js` cancels everything in one pass when you want to refresh.

## Security

- Credentials load from `.env` (gitignored); the password is base64-encoded, not plaintext.
- Login: run `npm run login` to log in on its own (add `-- --password-login` for the password flow). when the saved session expires the bot first tries to renew it from a saved refresh token (`refreshToken.json`, gitignored) with no input at all. If that fails it shows a QR code in the terminal; scan it with the Steam mobile app (Steam Guard tab -> "Scan a QR code") and approve. The QR path never reads your username or password, so `STEAM_USERNAME` / `STEAM_PASSWORD` can be removed from `.env`. A QR login saves a fresh refresh token, so you only need to scan again when Steam expires it (months). `refreshToken.json` is as sensitive as `session.json`: anyone who can read it can act as your Steam account on the website. The old username + password + typed Steam Guard code login is still available with `--password-login` (e.g. `node index.js --password-login`) or `STEAM_LOGIN_METHOD=password`.

## Disclaimer

Use at your own risk. Steam TOS prohibits automated market tools; this may lead to bans.
